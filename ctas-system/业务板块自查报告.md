# 审理辅助系统（CTAS）业务板块自查报告

> 自查日期：2026-10-24
> 自查范围：`backend/app/routers/trials.py`、`trial_materials.py`、`appeals.py`、`backend/app/sentencing.py`、`backend/app/decision.py`、`frontend/src/pages/Trials.tsx`、`frontend/src/App.tsx`
> 自查方式：静态代码通读 + 线上 API 实调 + 存量数据核对（未修改任何业务代码，未污染演示库）
> 结论：**主流程已闭环可用，但有 2 个真实缺口（1 个属业务闭环断裂）、11 项可优化点、6 项工程隐患**。建议按下表顺序推进，不建议并行铺开。

## 二、真实缺口（建议优先处理）

### 🔴 GAP-1　申诉复查「变更 / 撤销」后不闭环回原审理事项

**位置**：`backend/app/routers/appeals.py` → `conclude_appeal()`（第 352–414 行）

**现象**：复查结论作出「变更」或「撤销」时，代码只写 `Appeal` 表（`conclusion` / `status` / `decision_doc_id`），**完全不回写原 `Trial`**。后果：

- 原审理事项 `t.status` 仍停留在「已执行」，`decision_result` 仍是原档次（如"留党察看处分"），台账上看不出处分已被撤销或变更；
- 已报结的执行回证（`execution_closed=1`）不会被打开，`restore_rights_at` 也不会回滚——**权利恢复 / 职务恢复 / 待遇恢复这条纠错链在系统里断了**；
- 复查决定书正文已写明"恢复申诉人相关党员权利/公职待遇，并按规定恢复名誉"，但系统不据此驱动任何回证动作，两边数据不一致。

**对照《党员权利保障条例》《控告申诉工作条例》**：申诉复查结论属对原处分决定的否定性/变更性处置，必须落到原案执行状态上，否则"申诉期间不停止执行、结论后恢复权利"无法在系统内闭环。

**建议做法**（不臆断结论，只做结构与提示）：
1. `conclude_appeal` 中，当 `conclusion in ("变更", "撤销")` 时，在 `Trial` 上打纠错标记（如新增 `appeal_corrected` / `appeal_result` 两列），并在 `_trial_out` 中透出；
2. 自动把该 trial 的执行回证清单中受影响项（`rank_adj` 职务职级、`pay_adj` 工资待遇、`restore` 恢复党员权利）置回 `pending`，并清空 `execution_closed`（重新进入待落实状态），**留痕但不代填结论**；
3. 原决定书不删除，改为在台账与执行回证报告中显著标注"已由申诉复查程序变更/撤销"，避免"新旧两份决定书并存但看不出关系"；
4. 前端在 trial 详情增加"申诉复查结论"展示位与"回证需重新落实"提示。

**预计工作量**：中（后端约 60 行 + 前端约 40 行 + 自检 3–4 项断言）

### 🟡 GAP-2　处分决定书「二、主要违纪违法事实」未接审理报告已认定事实

**位置**：`backend/app/decision.py` 第 45 行

```python
facts = (case.content if case else "") or (trial.brief or "")
```

**现象**：决定书事实段直接取**案件登记时的原始案情**（`cases.content`），而不是**审理报告第三章已核验认定的违纪违法事实**。

**后果**（实测对照）：
- 李某案：案件登记原文为"多次收受管理服务对象礼金、财物共计折合人民币18.6万元…构成职务违法"；
- 审理报告第三章为同一段文字，但已经过证据链校验、证据印证标注；
- 对赵某案，案件原文是"审计发现赵某…审查调查组已查实**部分事实**"——决定书会把"仅部分事实查实"的登记状态直接写进正式处分决定书，而审理报告可能已补充完整事实。**两份文书事实口径可能不一致**，这是处分文书最不该出的错。

**建议做法**：
1. 决定书事实段优先取已定稿审理报告的第三章（`trial.report_doc_id` → `Document.content` 正则抽取"三、主要违纪违法事实"段）；
2. 取不到（尚未生成报告 / 未定稿）时，回落到现状并在段末标注"〔事实以审理报告第三章为准，本段取自案件登记材料〕"；
3. 若报告第三章与案件原文不一致，在决定书中**同时**列出并提示须人工核对，而不是静默取其一。

**预计工作量**：小–中（约 30 行 + 自检 2 项）

## 三、可优化点（按投入产出排序）

| # | 优化项 | 位置 | 说明 | 量级 |
|---|---|---|---|---|
| O1 | **涉案财物明细台账缺失** | `models.py` 无 `TrialProperty` 明细表 | 当前涉案财物只有两个自由文本字段（`involved_amount` 金额串 + `property_disposal` 处置意见串）。实务中收缴/责令退赔/登记上交需**逐项列明物品名称、数量、价值、权属、去向**，无法落台账、无法逐项核销，也无法支撑"是否全部执行到位"的判断 | 中 |
| O2 | **政务处分决定书未实现**（仅有提示语） | `decision.py` 第 104–109 行 | 公职人员案件在党纪决定书中只写一句"政务处分由监察机关另行作出"。**公职人员政务处分决定书是监察机关的正式法定文书**，与党纪处分决定书是两份平行文书，同案往往并行作出 | 中–高 |
| O3 | **人工填写的处分档次与量纪区间无一致性提示** | `decision.py` / `trials.py` | 承办人填"开除党籍处分"时，系统不提示该档次是否落在引擎给出的党纪/政务区间内。系统不代替裁量是对的，但**给一个"超出参考区间，请说明理由"的提示**能防止明显偏离 | 小 |
| O4 | **受理结论可在终态后被改写** | `accept_trial()`（第 1411 行） | 只拦了"不予受理不可重复受理"，但**未拦"已定稿/已执行案件被改回受理或暂缓受理"**，且改回时 `accepted_at` 被重置，SLA 计时重新开始，时限统计失真 | 小 |
| O5 | **退回补充调查未校验终态** | `return_trial()`（第 1497 行） | 只拦"已退回不可重复退回"，**未拦"已定稿/已执行案件被退回"**，会把已执行案件状态改成"退回补充调查"，与执行回证已报结的数据冲突 | 小 |
| O6 | **定稿后案件（cases）状态未回写** | `confirm_trial()`（第 1392 行） | `Trial.status` 置为"已定稿"，但关联 `Case.status` 不变（只在退回时会改）。案件台账与审理台账状态不同步 | 小 |
| O7 | **权限粒度不齐：回证回填、涉案财物处置、见面谈话、退回补证仅需登录** | `trials.py` 多处 `get_current_user` | 定稿/执行/决定书/报结用了 `require_roles("shenli","admin")`，但**回证回填、涉案财物处置、见面谈话、退回补证**任何登录用户都能改。其中"回证报结"是责任链末端动作、"退回补证"影响案件流向，权限应与定稿同级 | 小–中 |
| O8 | **无并发/乐观锁保护** | `models.py` `Trial` | 同一案件两个审理人员同时操作（如一边回填回证一边改涉案财物）会**后写覆盖先写**，且不留冲突痕迹。SQLite 部署下多人同时写的概率不低 | 中 |
| O9 | **决定书标题在"未填档次"时语义偏弱** | `decision.py` 第 65 行 | 未填档次时标题为"关于给予X党纪处分的决定"，但职务违法/职务犯罪案件本应体现政务处分线，标题语义需要更精确 | 小 |
| O10 | **审理报告与决定书事实口径无强绑定** | `POST /{tid}/decision` | 生成决定书时**不校验审理报告是否已定稿**，可在报告未定稿时先出决定书。实务中决定书应以定稿报告为据 | 小 |
| O11 | **`trials.py` 存在未使用的 LLM 依赖导入** | `trials.py` 第 17 行 `from app.llm import provider` | 全文件无 `provider.` 调用（grep 确认），是**死导入**。审理域全部走离线确定性引擎，与 P0 设计一致；但留着死导入会让人误以为审理链路依赖大模型，对信创无算力环境下的部署评估造成误导 | 极小（删 1 行） |

## 四、工程隐患（不阻塞业务，但建议排期）

| # | 隐患 | 影响 | 建议 |
|---|---|---|---|
| H1 | `get_db()` 无 `db.rollback()`（`database.py` 第 30–35 行） | 依赖 FastAPI 异常处理自动回滚；一旦有端点中途 commit 后再抛错，会留下**半成品数据**。当前 21 处 `audit.write_log` 均在 commit 之后，若审计写入失败不影响主事务，但反向不成立 | 显式 `except: db.rollback(); raise` |
| H2 | `trials.py` 单文件 1778 行 | 已超单文件可维护阈值，P4 之后继续加功能会加速劣化 | 后续拆分 `trials` 为 `trials_core` / `trials_report` / `trials_disposal` 三个子路由 |
| H3 | `regression_test.py` 2250 行 + `ctas_selfcheck.py` 469 行并存 | 两套测试职责重叠，回归时需人工判断跑哪个 | 明确 `ctas_selfcheck` 为 CTAS 域唯一回归入口，`regression_test` 标注为全业务域历史件 |
| H4 | `db_fix.py` / `db_fix_all.py` / `apply_replace.py` 留在项目根目录 | 一次性修库脚本混在业务代码旁，误运行有风险 | 移入 `backend/scripts/` 并加注释说明用途与执行前提 |
| H5 | `trial_materials.py` 的 `REQUIRED_CHECKLIST` 在 `_trial_out` 内**函数内 import** | 每次序列化 trial 都触发一次 import 查找，虽有缓存但语义不清，且隐式形成模块耦合 | 提到模块顶层 |
| H6 | 部分端点用 `Optional` / `list[dict] = []` 等可变默认值（Pydantic 已处理，但风格不统一） | `TrialReport.refs: list[dict] = []` 等在 Pydantic v2 下安全，但与文件内 `Optional` 混用，可读性差 | 统一风格 |

## 五、建议推进顺序（供后续有空时取用）

| 阶段 | 内容 | 理由 |
|---|---|---|
| **第 1 优先** | GAP-1 申诉复查纠错回写 + O4/O5 状态机补漏 + O11 死导入清理 | GAP-1 是闭环断裂（影响处分执行正确性）；O4/O5 是终态数据被改写的真实风险；O11 一行改动 |
| **第 2 优先** | GAP-2 决定书事实接审理报告 + O10 定稿校验 + O3 档次一致性提示 + O7 权限对齐 | 都是文书准确性与责任链一致性，量小收益高 |
| **第 3 优先** | O1 涉案财物明细台账 + O2 政务处分决定书 | 两者都是"独立模块级"工作量，牵连数据模型与前端，适合状态好时集中攻 |
| **第 4 优先** | O8 乐观锁 + H1 事务回滚 + H2 文件拆分 + H4 脚本归档 | 工程债，不影响业务正确性，可随功能迭代顺带清理 |
| **可延后** | O6 案件状态回写、O9 标题语义、H3/H5/H6 风格项 | 影响面小，可在相邻功能开发时顺手做 |
